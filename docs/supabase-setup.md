# Supabase setup for SaunakulaApp

This branch imports the useful idea from `MarinaOleinik/Saun_App`: bookings are checked against one shared cloud database instead of each phone keeping a separate SQLite file.

## Why this fixes the main architecture issue

Before:

```text
Phone A -> local saunakula.db3
Phone B -> local saunakula.db3
```

Both phones can book the same house for the same dates because they do not see each other.

After:

```text
MAUI View -> BookingViewModel -> SupabaseService -> Supabase PostgreSQL
```

Every device checks the same `reservations` table before creating a booking.

## Required Supabase tables

Run this in Supabase SQL editor if you create a fresh project:

```sql
create table if not exists houses (
    id bigint generated by default as identity primary key,
    app_house_id text unique not null,
    name text not null,
    description text
);

create table if not exists reservations (
    id bigint generated by default as identity primary key,
    house_id bigint not null references houses(id),
    customer_name text not null,
    start_date timestamptz not null,
    end_date timestamptz not null,
    created_at timestamptz not null default now()
);

insert into houses (id, app_house_id, name, description) values
    (1, 'soome', 'Soome maja', 'Finnish sauna house'),
    (2, 'jahimees', 'Jahimehe maja', 'Hunter house'),
    (3, 'vene', 'Vene maja', 'Russian sauna house'),
    (4, 'spa', 'SPA maja', 'SPA house')
on conflict (id) do update set
    app_house_id = excluded.app_house_id,
    name = excluded.name,
    description = excluded.description;
```

The teacher prototype currently has only three rows in `houses`, so `spa` must be added before all SaunakulaApp houses can be booked through the cloud database.

## Current mapping in code

`SupabaseService` maps existing app IDs to numeric Supabase IDs:

```text
soome    -> 1
jahimees -> 2
vene     -> 3
spa      -> 4
```

If the Supabase table uses different IDs, update `HouseIdMap` in `SaunakulaApp/Services/SupabaseService.cs`.
